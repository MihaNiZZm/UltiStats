# Дизайн lifecycle матчей

## Контекст

Issue #76 должен сделать жизненный цикл матча пригодным для проведения реальной игры. Сейчас разные причины отказа сводятся к `null` или `Boolean`, HTTP-коды неоднозначны, а времена начала, событий и завершения могут противоречить друг другу.

MVP работает для одного доверенного оператора в локальной сети. Несмотря на это, два HTTP-запроса могут пересечься из-за повторной отправки или задержки сети, поэтому проверка правила и запись должны выполняться атомарно.

## Цели

- Формализовать переходы `PLANNED -> IN_PROGRESS -> FINISHED`.
- Централизовать правила в чистой policy без доступа к БД.
- Различать отсутствие ресурса, невалидный запрос, запрещённое состояние и временной конфликт.
- Возвращать детерминированные HTTP-коды и `ProblemDetail` со стабильным машинным кодом.
- Не допускать противоречий между `startedAt`, `occurredAt` и `endedAt`.
- После успешной команды возвращать состояние, перечитанное после записи.

## Вне scope

- Правила последовательности типов игровых событий.
- Общий интерфейс или движок для всех будущих policies.
- Повторное открытие завершённого матча и обратные переходы состояния.
- Переименование частичного `PUT` в `PATCH`; это относится к #78.
- Ограничение timestamps относительно текущего времени сервера.
- Изменение правил удаления самого матча.

Будущая проверка допустимой последовательности игровых событий должна быть отдельной `EventSequencePolicy`. Она сможет использовать тот же архитектурный подход, но в #76 не создаются ни её интерфейс, ни заглушка.

## Архитектура

### `MatchLifecyclePolicy`

Отдельный stateless Spring-компонент, который получает уже загруженный `Match` и данные операции. Policy не использует репозитории, сервисы, транзакции или HTTP-типы.

Предполагаемые операции:

- проверка изменения команд или `plannedStartTimestamp`;
- проверка старта матча;
- проверка завершения матча;
- проверка создания события;
- проверка исправления существующего события;
- проверка удаления существующего события.

Policy возвращает разрешение или типизированное нарушение lifecycle. Она не изменяет переданный матч.

### Сервисы

`MatchServiceImpl` и `EventServiceImpl` отвечают за orchestration:

1. начинают транзакцию;
2. загружают актуальный матч с блокировкой строки;
3. вызывают `MatchLifecyclePolicy`;
4. при разрешении выполняют изменение;
5. перечитывают итоговое состояние;
6. возвращают типизированный результат.

Сложные проверки нескольких сущностей в будущем должны жить в orchestration-сервисах: такой сервис загружает необходимые сущности и передаёт их в независимые policies.

### Фасады и контроллеры

- Фасад преобразует успешную доменную модель в response DTO и сохраняет конкретную причину отказа.
- Контроллер отображает результат в HTTP и создаёт `ProblemDetail`.
- Policy не знает о статусах HTTP.

## Переходы состояния

| Операция | `PLANNED` | `IN_PROGRESS` | `FINISHED` |
|---|---:|---:|---:|
| Изменить команды или `plannedStartTimestamp` | разрешено | `409` | `409` |
| Начать матч | разрешено | `409` | `409` |
| Завершить матч | `409` | разрешено | `409` |
| Создать событие | `409` | разрешено | `409` |
| Исправить существующее событие | `409` | разрешено | разрешено |
| Удалить существующее событие | `409` | разрешено | разрешено |

Повторный старт, повторное завершение и повторное открытие завершённого матча запрещены.

Исправление события не меняет его тип и `occurredAt`; текущий API позволяет исправлять участников. После исправления или удаления пересчитывается кэш счёта, а статистика при следующем чтении строится по обновлённому event log.

## Временные инварианты

- `plannedStartTimestamp` является информационным: фактический старт может быть раньше или позже плана.
- `startedAt` не может быть позже самого раннего активного события.
- Новое событие может быть создано только в `IN_PROGRESS`.
- `occurredAt` нового события не может быть раньше `startedAt`.
- `occurredAt` нового события не может быть раньше предыдущего активного события в event log.
- `endedAt` не может быть раньше `startedAt`.
- `endedAt` не может быть раньше последнего активного события.
- Равенство допустимо: событие может произойти ровно в `startedAt`, а матч может завершиться ровно во время последнего события.
- Wall-clock ограничения не вводятся: проверяется внутренняя хронология матча, а не расхождение часов устройств.

Проверка самого раннего события при старте сохраняется как защитный инвариант, даже если новые события больше нельзя создавать до старта.

## Типизированные результаты

Команды матча используют результат следующей формы:

```kotlin
sealed interface MatchCommandResult<out T> {
    data class Success<T>(val value: T) : MatchCommandResult<T>
    data object NotFound : MatchCommandResult<Nothing>
    data class InvalidRequest(val problem: MatchProblem) : MatchCommandResult<Nothing>
    data class InvalidState(val problem: MatchProblem) : MatchCommandResult<Nothing>
    data class Conflict(val problem: MatchProblem) : MatchCommandResult<Nothing>
}
```

Разделение причин:

- `InvalidRequest`: запрос не может быть применён независимо от текущего состояния, например неверное количество команд, дубликаты ID или отсутствующая указанная команда.
- `NotFound`: целевой матч отсутствует.
- `InvalidState`: операция не разрешена в текущем статусе матча.
- `Conflict`: статус допускает операцию, но она нарушает временную шкалу или другое текущее состояние данных.

Для создания события существующий `EventResult` расширяется эквивалентными `InvalidState` и `Conflict`. Правила последовательности типов событий не добавляются.

## HTTP-контракт

Существующие маршруты сохраняются:

- `POST /api/v1/matches/{id}/start`;
- `POST /api/v1/matches/{id}/end`;
- `PUT /api/v1/matches/{id}` с текущей семантикой частичного обновления;
- существующие endpoints событий.

Маппинг результатов:

- `Success` -> текущий успешный код endpoint (`200`, `201` или `204`);
- `InvalidRequest` -> `400 Bad Request`;
- `NotFound` -> `404 Not Found`;
- `InvalidState` -> `409 Conflict`;
- `Conflict` -> `409 Conflict`.

Ошибки возвращаются как Spring `ProblemDetail`. Помимо стандартных полей ответ всегда содержит стабильный `code`. Для `InvalidState` ответ также содержит `currentStatus`; для остальных ошибок это поле отсутствует.

Пример:

```json
{
  "type": "about:blank",
  "title": "Match state conflict",
  "status": 409,
  "detail": "Events can only be created while the match is in progress",
  "instance": "/api/v1/matches/{matchId}/events",
  "code": "MATCH_NOT_IN_PROGRESS",
  "currentStatus": "FINISHED"
}
```

Первоначальный набор кодов:

- `INVALID_REQUEST` для общего отказа в применении некорректного запроса;
- `RESOURCE_NOT_FOUND` для отсутствующего целевого матча или события;
- `MATCH_NOT_IN_PROGRESS`;
- `MATCH_ALREADY_STARTED`;
- `MATCH_NOT_STARTED`;
- `MATCH_ALREADY_FINISHED`;
- `MATCH_UPDATE_LOCKED`;
- `START_AFTER_FIRST_EVENT`;
- `END_BEFORE_START`;
- `END_BEFORE_LAST_EVENT`;
- `EVENT_BEFORE_START`;
- `EVENT_OUT_OF_ORDER`.

Новые коды без доказанной необходимости в #76 не добавляются. `INVALID_REQUEST` и `RESOURCE_NOT_FOUND` необходимы, чтобы выполнить уже согласованный контракт обязательного стабильного `code` для `400` и `404`; это не lifecycle-нарушения.

## Транзакции и конкуренция

Lifecycle-команды загружают строку матча с pessimistic write lock внутри активной транзакции. Одинаковая блокировка используется для:

- изменения матча;
- старта и завершения матча;
- создания, исправления и удаления события.

Это сериализует конфликтующие команды. Например, `end match` и `create event` не смогут одновременно пройти проверки на разных версиях состояния: второй запрос увидит результат первого и либо выполнится безопасно, либо получит `409`.

Изменение схемы БД для блокировки не требуется.

## Тестирование

### Unit-тесты policy

Табличные тесты покрывают:

- каждое действие во всех трёх статусах;
- матч без событий;
- границы `startedAt`, первого события, последнего события и `endedAt`;
- допустимое равенство timestamps;
- каждую конкретную причину отказа.

### Service/integration-тесты

Через Spring/JPA проверяются production-пути:

- разрешённый переход сохраняется;
- запрещённый переход не меняет данные;
- успешная команда возвращает перечитанное состояние;
- создание события запрещено в `PLANNED` и `FINISHED`;
- создание события разрешено в `IN_PROGRESS` при корректном времени;
- после `FINISHED` существующее событие можно исправить и удалить;
- после исправления или удаления пересчитывается кэш счёта, а статистика отражает обновлённый event log;
- блокировка сериализует конфликтующие lifecycle-команды.

### Controller contract-тесты

Проверяются точные коды ответа, JSON shape `ProblemDetail`, `code` и `currentStatus` там, где он применим.

### PostgreSQL и удалённый стенд

- Выполняется чистый запуск и интеграционная проверка на PostgreSQL.
- После локальной проверки разрешено провести smoke-test на удалённом стенде.
- Все созданные на стенде команды, игроки, матчи и события получают уникальный тестовый префикс.
- Во время теста сохраняются точные ID созданных ресурсов.
- Cleanup удаляет только созданные тестом ресурсы в обратном порядке зависимостей.
- После cleanup выполняется проверка, что каждый сохранённый ID более недоступен.
- Массовое удаление, очистка таблиц и удаление чужих данных запрещены.

## Критерии готовности

- Все переходы и временные инварианты реализованы через `MatchLifecyclePolicy`.
- Policy не имеет зависимостей на persistence или HTTP.
- Проверка и изменение выполняются в одной транзакции над заблокированным актуальным матчем.
- Несуществующий матч всегда даёт `404`.
- Невалидный запрос даёт `400`.
- Запрещённый переход или временной конфликт даёт `409` с детерминированным `ProblemDetail.code`.
- После успешного старта или завершения возвращается перечитанное состояние.
- Все согласованные unit-, integration- и controller-тесты проходят.
- При использовании удалённого стенда созданные тестовые данные полностью удалены по известным ID.
